# OnSET: Disclaimer

OnSET (Ontology and Semantic Exploration Toolkit) is a research tool for exploring and querying ontologies and knowledge graphs through natural-language input and a visual query editor; it has no clinical function.

> **Research use only. Not a medical device.**
> This software was developed in the HEREDITARY project as a research prototype. It has not been assessed or certified under the EU Medical Device Regulation (EU) 2017/745. It must not be used to diagnose, treat, monitor or make any other decision about individual patients.

## Intended use

**Intended use.** Exploring ontologies and knowledge graphs (KGs) without writing SPARQL. A user states an information need in natural language; a local language model, constrained by a grammar built from the ontology in use, turns it into a prototype query graph; the user inspects and edits that graph in a node-link editor and runs it as SPARQL against the KG. Further views show topics (a topic model over ontology labels), the class hierarchy and the links between classes.

**Intended users.** Researchers in knowledge graphs, information retrieval and visualisation; biomedical researchers acting in a research capacity; developers building query interfaces on top of HEREDITARY knowledge graphs.

**Out-of-scope uses.**
- Clinical diagnosis, prognosis, treatment or monitoring of individual patients.
- Any decision about an individual person (care, insurance, employment).
- Re-identification of persons, or linking KG content to individuals.
- Loading knowledge graphs that contain personal or patient-level data; this has not been assessed.
- Treating query results as health claims without checking the underlying source triples.

## Data provenance

The repository does **not** contain any knowledge-graph data. KGs are fetched and indexed locally with [QLever](https://github.com/ad-freiburg/qlever-control) using the `Qleverfile`s in `docker/*-data`:

| Dataset | Source | Type | Notes |
|---|---|---|---|
| DBpedia | https://www.dbpedia.org/ (`docker/dbpedia-data`) | Public | General encyclopaedic KG; used in the user study and the default backend configuration |
| UniProt core ontology | https://ftp.uniprot.org/ (`docker/uniprot-data`) | Public | `docker/uniprot-data/owl/core.owl` is committed |
| BRAINTEASER Ontology (BTO) | https://zenodo.org/records/12789731 (`docker/bto-data`) | Public ontology | `docker/bto-data/download.sh` also merges any BRAINTEASER ALS/MS dataset TTL files found under the git-ignored `data/datasets/` folder; these are not part of the repository |
| YAGO, DNB, DBLP, Olympics | Public dumps (`docker/yago-data`, `docker/dnb-data`, `docker/dblp-data`, `docker/olympics-data`) | Public | Each under its own open licence |
| Language and embedding models | Hugging Face Hub (see Method) | Public model weights | Used as released, not fine-tuned; downloaded at runtime, not committed |

The committed files under `exploration/` and `test.json` hold ontology class/relation labels and similarity scores from development experiments, plus aggregated evaluation tables (`exploration/querying/tables`). Raw user-study data is excluded from the repository (`**/user-study/private` is git-ignored).

## Method

- **Query extraction.** A language model run locally with [llama-cpp-python](https://github.com/abetlen/llama-cpp-python) extracts entities and relations from the natural-language query. Similar existing classes and relations are retrieved by sentence-embedding search (stored with pgvector in PostgreSQL), and a second pass, constrained by a GBNF grammar generated from those candidates, produces a prototype graph that only uses classes and relations present in the ontology. The graph is edited in the browser and executed as SPARQL against the QLever endpoint.
- **Topics.** A BERTopic model over ontology labels, with topic labels generated by the same local language model.
- **Training.** Nothing is trained or fine-tuned. Embeddings and topic models are computed at deployment time from the ontology's labels.
- **Caching.** Query strings, prototype graphs and assistant operations are cached in Redis; embeddings and topics are stored in PostgreSQL.
- **Privacy techniques.** None; the tool is designed for public, non-personal knowledge graphs.
- **Outside services.** No hosted LLM API (OpenAI, Anthropic, Gemini or similar) is called; all inference runs on the server. The backend (server side) downloads model weights from the **Hugging Face Hub** when it first starts: the GGUF language model set in `backend/src/eval_config.py` (by default `NousResearch/Hermes-3-Llama-3.1-8B-GGUF`, overridable with `LLM_MODEL_ID`/`LLM_MODEL_QUANT`), the embedding model `dunzhang/stella_en_400M_v5` (loaded with `trust_remote_code=True`) and, for the dataset matcher, `sentence-transformers/all-MiniLM-L6-v2`. No user input is sent to Hugging Face. The browser only talks to the OnSET backend (`ONSET_API_BASE_URL`).

## Performance

- **Query extraction.** Evaluated offline on generated queries over DBpedia, UniProt, BTO, YAGO and DNB, comparing several local models (3B to 32B parameters) by graph-extraction F1 and normalised graph edit distance; tables in `exploration/querying/tables/compare_model_*.tex` and deliverable D5.5.
- **User study.** 11 participants, all with a computer-science background, on DBpedia (D5.7; `exploration/querying/tables/task_results.tex`): all participants placed all nodes correctly in all four tasks; links were correct in 82-100 % and whole queries in 73-100 % of cases per task.
- **Subgroups.** Not reported; the study is too small and homogeneous, and no clinical users took part.

## Known limitations and risks

- **Generalisability.** Extraction quality depends on the ontology and the model and has only been measured on the KGs listed above. A new ontology needs new embeddings and a new topic model, and the reported figures do not carry over.
- **Failure modes.** The model can produce a well-formed query graph that encodes a different relation than the one intended; results then look plausible but answer a different question. The editable query graph and the displayed SPARQL exist so that this can be checked. Long multi-clause questions and very large ontologies reduce extraction quality; queries on large graphs can time out.
- **Biases.** Results reflect the content of the loaded KG. Literature- or crowd-derived KGs contain extraction errors and publication or coverage bias; a missing relation means "not in the graph", not "not true".
- **Privacy.** No personal data is processed by design. User queries are cached server side (Redis/PostgreSQL), so users must not enter personal or patient data.
- **Security of the reference setup.** The bundled `docker/onset-data/docker-compose.yml` uses development default credentials (`postgres`/`postgres` for PostgreSQL and pgAdmin), and the `Qleverfile`s contain fixed QLever access tokens; change both for any exposed deployment. The backend allows all CORS origins, exposes an unauthenticated SPARQL pass-through (`/sparql`) and an ontology upload endpoint (`/management/ontology`). The embedding model is loaded with `trust_remote_code=True`, which executes code from its Hugging Face repository.
